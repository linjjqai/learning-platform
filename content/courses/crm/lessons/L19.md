# 速览（30 秒看完）

- 交易管理的核心场景是：产品上架 → 报价 → 签合同 → 下单 → 发货 → 收货 → 回款 → 开票，涵盖从报价单到开票申请的全交易闭环。
- 物料管理先于交易管理：新建产品前必须先建产品分类；产品有"上架/下架"状态，已下架产品不可再选。
- 三个核心字段：标准价格（参考价）、上下架（销售状态）、多单位配置（不同计量单位不同价格）。
- 价目表是本课重点，用于对不同等级客户、不同区域、不同销售人员设置差异化价格，比手工改价高效且规范。
- 价目表关键开关在管理后台→业务规则管理→销售管理配置→价格管理配置，一旦启用无法关闭，需谨慎操作。
- 价目表可叠加有效期（不同时间段不同价格）、阶梯价格（不同购买数量不同单价）、多单位定价、商品规格组合价格。
- 可售范围是价目表的上层限定，定义某组织/人员可向哪些客户卖哪些产品；可售范围 ≤ 价目表范围时以可售范围为准。
- 交易对象关系：报价单（主）↔ 报价单明细（从），销售合同（主）↔ 合同明细（从），销售定单（主）↔ 定单产品（从），回款计划（主）↔ 回款（从）。
- 合同与定单是一对多关系：一份销售合同可通过"合同转定单"按钮衍生多个销售定单。
- SPU/SKU 概念：商品（SPU）是基础产品单元，规格（颜色、内存等）与规格值组合生成不同的 SKU 产品。系统需开启"商品配置开关"后才有商品/规格/规格值三个对象。

## 核心要点

- **课程序言与前情回顾**：讲师张政宇，本课讲交易管理模块。回顾前几课学过的线索、商机、客户三个对象，以及它们之间的区别——线索是对客户购买意向尚未确定的信息，客户是已基本确认能转化的购买主体。
- **交易管理核心场景**：以一个完整的电商为例——公司上架产品（X 手机 3000 元、Y 手机 4000 元、充电器 50 元），给 A（重要客户）和 B（一般客户）两个不同级别客户报不同价格，最终完成报价→合同→定单→发货→回款→开票的闭环。
- **产品分类**：新建产品前必须先维护产品分类（办公用品、数码产品、服务等）。好处是后期可按分类做销售统计，判断哪类产品卖得好、需要重点备货。
- **产品关键字段**：标准价格（参考价，非最终成交价）、上下架状态（下架产品在销售定单中不可选）。上架/下架在实际业务中常用：服装行业换季时下架反季款，科技产品出新一代时下架旧代。
- **差异化定价问题**：针对不同等级客户设置不同价格（如重要客户 X 手机 2500 元、一般客户 2800 元）。方案一：在定单产品里手动改价，适合一两个客户；方案二：用价目表批量配置，适合大量客户。
- **价目表定义与适用场景**：价目表可针对不同客户群体、不同产品设定价格，还支持有效期、多单位阶梯价。典型场景：不同等级客户差异化定价、不同区域（北京卖北冰洋、陕西卖冰峰）产品差异、不同等级销售人员价格不同（业绩好的卖得更便宜以激励）。
- **价目表配置实操**：价目表名称建议含客户级别以便识别，有启用开关、有效期（开始时间—结束时间）、使用组织（指定哪些人员/区域/客户适用），然后添加产品并填入具体价格。
- **价目表有效期**：同一产品在不同时间段卖不同价格（如国庆活动期间 X 手机 2100 元，活动后恢复 2200 元）。两种实现方式：在一个价目表内配不同有效期的产品行，或建两个独立价目表——前者更高效。
- **后台开关**：管理后台→业务规则管理→销售管理配置→价格管理配置，有价目表开关、价目表明细选产品开关。**一旦启用无法关闭**，操作前务必确认登录的是自己的测试环境还是客户账号。
- **指定条件 vs 指定客户**：价目表适用客户时，可选择"符合指定条件"或"指定客户"。前者按客户属性自动匹配，新建符合条件的客户自动纳入；后者需手工一个个添加。推荐用"指定条件"，维护成本更低。
- **阶梯价格与多单位**：外手机数量不同（≤10 台 3500 元、11–20 台 3200 元、≥21 台 3000 元）对应不同单价，通过价目表明细支持的"阶梯价格"实现。前提是打开"多单位"开关——开关在后台商品产品配置里，还需要申请相关灰度权限。
- **可售范围**：定义"在什么时间范围、什么人员组织、针对什么客户、可以卖什么产品"。它与价目表形成两层限定：可售范围 ≤ 价目表范围时以可售范围为准，可售范围 ≥ 价目表范围时以价目表为准。目前实际使用场景不多，简单了解即可。
- **完整交易流程演练**：报价单 → 转销售合同 → 转销售定单 → 圈发货/圈收货（真实环境有独立发货单和收货单对象）→ 回款计划 → 回款 → 开票申请。全程在系统内留痕。
- **价目表在交易中的使用**：新建报价单时先选客户再选价目表（重要客户价目表/一般客户价目表），系统自动带出对应产品和价格。讲师演示中先选价目表再选产品，是正确顺序。
- **回款计划与回款**：回款计划支持"新建（单条）"和"批量新建（按定单金额自动平分成 N 期）"。回款时关联回款计划，回款金额不能超过计划金额，可分多次回款覆盖同一计划。
- **报价单高级功能**：同一客户的"历史报价"可快速调出参考；同一产品的"历史售价"可查看价格变化轨迹，防止报价过低或过高。
- **合同与定单的一对多关系**：业务上通常先签一份销售合同，后续通过"合同转定单"按钮衍生多份销售定单来履行合同。这是 CRM 交易管理的标准业务模型。
- **回款计划适用场景**：长周期交易（如项目型销售，周期一年以上），回款分多期（预付 30%、中期 40%、验收后 30%）。回款计划帮助销售和财务提前安排催收节奏，降低回款风险。
- **退货与退款**：产品有瑕疵需退货退款时，系统有"退货单"和"退款单"两个对象——退货单处理实物退回，退款单处理资金退回，两者可关联原销售定单。
- **商品/规格/SKU 体系**：SPU（商品）是基础，如"X 品牌笔记本"；规格有两个维度——颜色（白/黑）、内存（128G/256G）；四个规格值组合生成四个 SKU 产品。需开启后台"商品配置开关"才能使用，配置后销售时按规格值组合选产品。
- **整体知识结构**：交易管理 = 物料管理 + 交易流程。物料管理先配产品分类→产品→多单位→商品→规格，可选配价目表和可售范围；交易流程从报价单到开票申请闭环，可走退货退款。后台提供"交易管理配置首页"帮助排查设置。
- **数据分析与 BI**：交易数据积累后，管理者按部门/人员分析成交金额、回款金额、逾期回款金额，判断业绩达成；可通过 BI 报表按产品分类、地区分布、月度回款趋势多维度分析。BI 用得深入与否是判断客户 CRM 使用成熟度的核心标志。
- **价值总结**：传统合同靠 Excel 管理（版本混乱、数据不齐、无法追溯审批），传统回款靠人工催款（无计划、风险高）。CRM 统一规范产品、流程留痕可追溯、回款计划提前预警，数据完整后支撑科学决策。

## 结构与流程

物料管理（交易前配置）：

```
产品分类维护 → 新建产品（标准价格 + 上下架）
 │
 ├── 多单位配置（不同计量单位不同价格）
 ├── 商品配置（商品 + 规格 + 规格值 → SKU 组合产品）
 │
 └── 价目表配置 ★
 ├── 适用客户（指定条件 / 指定客户）
 ├── 有效期（开始 — 结束，可配多段）
 ├── 阶梯价格（不同数量不同单价）
 └── 多单位定价

可售范围（可选，价目表上层限定）
```

完整交易流程：

```
报价单 ──→ 销售合同 ──→ 销售定单 ──→ 发货单 ──→ 收货单
 │ │ │
 │ └──合同转定单──┘
 │
 ├── 回款计划（分多期）──→ 回款（可多次覆盖同一计划）
 │
 └── 开票申请

异常流程：
销售定单 → 退货单（实物退回）→ 退款单（资金退回）
```

## 术语表

| 术语 | 含义 |
| --- | --- |
| 价目表 | 针对不同客户群体/区域/销售人员定义差异化产品价格的核心对象，支持有效期、阶梯价格、多单位 |
| 阶梯价格 | 同一产品按不同购买数量区间设置不同单价 |
| 多单位 | 同一产品支持不同计量单位（如"台"和"箱"）分别定价 |
| 可售范围 | 价目表的上层限定，定义某人员组织可向哪些客户卖哪些产品 |
| SPU（商品） | 标准产品单元，如"X 品牌笔记本" |
| SKU | 库存量单位，商品与规格值组合后的具体产品（如白色 128G 笔记本） |
| 规格 | 产品属性维度，如颜色、内存 |
| 规格值 | 规格的具体选项，如颜色的规格值是白色/黑色 |
| 销售合同 | 业务上一份合同可衍生多份销售定单履行，与定单是一对多关系 |
| 报价单 | 交易起始文档，向客户报出产品价格明细，支持转销售合同 |
| 回款计划 | 将大额回款拆分为多期，每期待回款金额和日期明确，支持批量自动生成 |
| 开票申请 | 交易末端，根据回款情况开具发票的申请文档 |
| 产品标准价格 | 产品统一参考价，非最终成交价，与实际销售价可能不同 |

## 需要注意的点

1. **后台开关不可逆**：价目表开关、价目表明细选产品开关、多单位开关、商品配置开关一旦启用无法关闭。操作前必须确认当前登录的是测试环境还是客户账号。
2. **价目表用"指定条件"不用"指定客户"**：前者自动匹配客户属性，新建符合条件的客户自动纳入覆盖；后者需手工一个个添加，大量客户时维护成本极高。
3. **新建报价单时先选价目表再选产品**：讲师演示过先选产品后选价目表导致混乱的情况，正确顺序是先选价目表让产品池自动限定，再选产品和填数量。
4. **合同与定单的业务关系**：一份合同可对应多份定单，不要反过来建"一份定单多份合同"的数据模型。
5. **多单位功能需灰度申请**：不是所有账号默认开启，需要在产品配置里打开开关并申请相关灰度权限。
6. **BI 是 CRM 成熟度的晴雨表**：客户能按产品分类、地区、人员多维度做分析时，说明交易管理已跑通且数据质量高。
