# 速览（30 秒看完）

- 审批流＝把企业线下的审批制度搬到线上，配置入口是【管理后台】—【流程管理】—【审批流程管理】—【新建】。
- 一条审批流走三步：基本信息（名称、发起身份、触发时机）→ 节点设计 → 后动作。
- 触发时机有六种：新建、编辑、作废、变更负责人、阶段变更、其他按钮（比如从公海点"领取"）。
- 节点类型有六种：普通审批、多分支、任务协作、并行网关、等待、操作节点。
- 审批类型分三类五种：普通审批（多人审批 / 会签）、层级审批、逐级审批（固定级数 / 固定级别）。
- 后动作要看位置：节点上方的"后动作"只管本节点，左下方的"执行操作"是整条流程结束后才执行。
- 三条硬限制：逐级审批的节点内不支持加签；加签人只能提意见、不能决定通过或驳回；阶段变更类审批流没有"审批通过后动作"。
- 两道配置题固定考法：销售订单折扣 8 折报备、合同按区域 + 按产品折扣审批。

## 核心要点

- **审批流的定义**：把企业线下的行为制度线上化，让各种制度在流程里体现，保证数据的正确性和完整性；同时把相关环节串起来，保证各个环节正常运转、提高企业内数据流转效率。
- **课件给的三条价值**：① 灵活配置与信息流转——审批规则、审批人都能灵活配，支持多种审批方式，顺带核准数据的有效性和操作权限；② 效率提升与制度线上化——业务数据完整、制度高效执行、降低管理成本；③ 数据及数据核准——领导确认之后，往往还要相关职能部门的专业人员在对应环节再确认一遍，所以流程里要加财务、法务这类人。
- **配置入口与三步逻辑**：【管理后台】—【流程管理】—【审批流程管理】—【新建】。之后依次是：① 基本信息（审批流名称、以什么身份发起、何时触发、对哪个对象）；② 节点设计（多分支 + 各类审批/协作节点）；③ 后动作（节点后做什么、流程后做什么）。
- **基本信息-命名**：按业务场景 + 内容命名（如"销售订单折扣审批"），不要叫"审批1"；流程一多，名字含糊就找不到。有个 APALM 字段是系统自动生成、给研发做数据存储用的，不用管。
- **基本信息-发起身份：数据提交人 vs 数据负责人**：助理 A 帮销售 B 建了一条商机、负责人填的是 B——这条数据的创建人（提交人）是 A，负责人是 B。审批人要"本级部门负责人"时，选"数据提交人"发起，批的是 A 所在部门的负责人；选"数据负责人"发起，批的是 B 所在部门的负责人。判断"上级是谁""哪个部门"都跟着这个选择走。
- **基本信息-跨组织审批**：勾选后才能让上下游公司、外部系统里的供应商/客户参与审批；纯内部审批不用勾。
- **触发时机有六种**：① 新建时——新建某个对象的数据，如客户报备审批；② 编辑时——编辑某条数据，如修改商机金额要审核；③ 作废时——作废某条数据，如作废某笔订单；④ 变更负责人时——更换某条数据的负责人，如换客户负责人；⑤ 阶段变更时——数据用了阶段推进器且阶段发生变更，如商机阶段推进；⑥ 其他按钮——系统预置或自定义按钮被点击，如从公海点"领取"。
- **总是触发 vs 满足条件触发**："总是触发"＝该对象每次新建/编辑都走审批；"满足条件触发"＝达到设定条件才触发，如订单折扣 ≥8 折才走报备。条件里还能用系统变量卡发起人范围——只有"营销中心"的人建的订单才走这条流，财务部的人建单就不走；多组条件之间可以设"或"，满足任一组就触发。
- **多分支（条件分支）节点**：一个环节能分出多条并行审批路径，不同路径的审批人、条件各不相同。折扣 ≥50% 走总经理、<50% 走部门负责人，分流就在这里做。配的时候先连线、再配条件，连线完成后"审批条件"下拉里才选得到目标节点。
- **节点类型共六种**：① 普通审批——最基础的审批环节，做简单审批和流程控制；② 多分支；③ 任务协作——节点处理人中任何一人完成相应操作即可；④ 并行网关；⑤ 等待——暂停流程，等特定条件或事件发生；⑥ 操作节点——执行具体的操作或任务，如审批、通知、数据处理。只让人签字用普通审批，要几个人分工填不同字段就用任务协作 + 并行网关。
- **并行网关怎么用（课件案例）**：项目评审环节，不同部门的人协作评审、每个人要编辑的字段都不一样，评完之后流程还要按大家填的字段值综合判断往哪走——做法是把多个任务协作节点放进并行网关同时处理，所有分支任务全部完成后流程才向后流转。
- **节点处理人的九个维度**：① 同事（通讯录里的人）；② 部门（组织架构里的部门，整个部门都能批）；③ 部门负责人；④ 用户组（单独创建的虚拟组织，如"活动筹备组"）；⑤ 角色（CRM 角色，如销售人员、财务人员）；⑥ 审批角色（具备特殊审批权限、可以审批某个部门发起的审批）；⑦ 流程相关变量（发起人、发起人主属部门负责人）；⑧ 数据相关变量（数据负责人、负责人上级、团队成员、团队成员上级）；⑨ 人员对象变量（对象上人员类型字段，如订单里有个"实施人员"字段，就把这个人设为审批人）。
- **审批类型只有三类五种**：普通审批（再分多人审批 / 会签）、层级审批、逐级审批（再分固定级数 / 固定级别）。配置前先想清楚审批流程该怎么走，再决定用哪一种。
- **多人审批 vs 会签**：普通审批直接指定具体审批人；选了多个审批人时，可以设多人审批或会签——多人审批只要其中一人同意就视为通过，会签要所有审批人都同意才视为通过。
- **层级审批**：直接由某一级部门的负责人审批，配置里可选"本级部门"这类层级选项。例：审批人就是发起人本级部门的负责人，选"本级部门"即可。课件特别提示，这个选项的前提是"不考虑部门负责人自己提交审批"的情况——负责人本人提交时，得另行处理。
- **逐级审批——固定级数 vs 固定级别**：都按部门层级逐级往上批。固定级数＝指定要几个部门批，选 2 就是提交人所在部门负责人批完、再由上一级部门负责人批，一共 2 个部门负责人；固定级别＝指定审批终点，选"1 级部门负责人"就是不管谁提交，都从提交人所在部门一路批到组织架构里第 1 级部门的负责人。
- **后动作分两处，位置决定时机**：节点配置里上方那块是"后动作"，只管当前这个节点完成后系统要做什么；左下方那块叫"执行操作"，是整条审批流程都结束以后才执行。两处配错，动作就会提前或延后触发。
- **后动作能做什么（八种）**：字段变更、短信通知 / 邮件通知、发起业务流程、外部通知、执行自定义函数、CRM 提醒、更换负责人、数据锁定 / 解锁。其中外部通知是给下游代理商这类对象发 CRM 通知，要先购买纷享销客互联产品。
- **后动作的典型配法**：报销审批通过 →字段变更把"报销状态"改成"已报销"；商机审批通过 →发起业务流程，自动走"实施立项"；审批通过 →锁定数据，驳回 →CRM 提醒发起人"审批已驳回"；审批通过 →更换负责人，把单子交给客户成功团队继续跟进。
- **固定审批 vs 自由审批**：固定审批＝节点、处理人、条件全在后台配死，前端人员只负责点提交；自由审批＝后台只配默认处理人，发起人在提交时自己挑审批人。同一个对象二选一，选了固定就不能用自由。
- **加签——前加签 / 后加签**：审批中途发现还需要别人给意见时用。前加签＝点"同意"之前先找人批；后加签＝点"同意"之后再补找人；都支持串行（依次批）和并行（同时收到）。两条硬限制：逐级审批的节点内不支持加签；加签人只能提供意见，不能改变审批流程、也无法决定通过或驳回。
- **阶段变更触发审批**：数据用了阶段推进器、阶段发生变更时触发，不是新建时触发。这类审批流没有"审批通过后动作"，只有节点完成后动作——想让阶段审批通过后锁单、发提醒，得配在节点后动作里。
- **配置题1——按层级选对审批类型**：组织架构是 销售中心（1 级）→ 直属/直营部（2 级）→ 各大区（3 级），大区下面还有售前组。华北大区销售要一路批到全公司负责人 → 逐级审批；只往上批 2 级 → 逐级审批固定级数选 2；华北售前组的售前顾问要直接由直营部负责人批 → 层级审批选 2 级部门负责人；只要销售中心的人批 → 层级审批指定对应级别。
- **配置题2——销售订单折扣报备**：营销中心下设销售一部/二部/三部，下面还有小组，销售人员建单即触发。折扣 ≥8 折（含 8 折）→ 本部门负责人（层级审批"本级部门"）+ 财务部（普通审批）；折扣 <8 折 → 逐级审批到营销中心部门负责人 + 财务部普通审批。后动作：通过 →数据自动锁定；驳回 →CRM 提醒发起人"审批已驳回"。
- **配置题3——合同审批**：销售经理提交合同 → 直属领导先审；再按区域（华东、华南、华北、华中）由对应区域项目经理审，用多分支按区域一路分一路；再判断产品是否超过最低折扣 8 折，超过才给市场部负责人审，没超过直接跳过；通过后第一时间通知仓库部门备货——用 CRM 提醒通知仓库，再发起业务流程触发发货流程。

## 结构与流程

审批流配置逻辑：

```
第一步：基本信息
 审批流名称（建议业务+内容命名）
 发起身份：数据提交人 / 数据负责人
 跨组织审批（仅上下游协作时勾选）
 发起对象（哪个对象的审批）
 触发时机：新建时 / 编辑时 / 作废时 / 变更负责人时 / 阶段变更时 / 其他按钮
 锁定关联从数据（默认勾选）

第二步：节点设计
 开始 → 多分支（可选）→ 普通审批 / 任务协作 / 并行网关 / 等待 / 操作节点 → ... → 结束

第三步：后动作
 节点后动作（节点上方）：字段变更 / 短信 / 邮件 / CRM提醒 / 发起业务流程 /
   外部通知（需购互联产品）/ 执行自定义函数 / 换负责人 / 数据锁定解锁
 流程后动作（左下方"执行操作"）：整条审批结束后才执行；阶段变更类审批流没有这一项
```

审批类型对比：

```
普通审批-多人审批  任一人同意即通过            场景：部门内部签字
普通审批-会签      所有审批人都同意才通过      场景：法务+财务联合审核
层级审批           直接由某一级部门负责人审批  场景：选"本级部门"按层级取人
逐级审批-固定级数  指定要批几个部门（如 2 级）  场景：往上找两级负责人
逐级审批-固定级别  指定审批终点（如 1 级部门）  场景：一路批到组织架构第 1 级
```

## 需要注意的点

1. **一个对象只能有一个审批流类型**——选了固定审批就不能用自由审批，反之亦然。
2. **先确定发起身份再配节点**：选"数据提交人"还是"数据负责人"，直接决定处理人按谁的部门、谁的上级去找。
3. **条件分支节点要先连线再配条件**：画好流程线后，审批节点的"审批条件"下拉框里才会出现目标节点，否则选不到。
4. **普通审批 vs 会签不要混**：普通审批多人时"任一人同意即通过"；会签要"所有审批人都同意"。法务和财务都得签字，就用会签。
5. **固定级数 vs 固定级别**：固定级数（如往上 2 级）不管公司多少层，就往上找 2 层；固定级别（如 1 级部门负责人）不管发起人在哪层，都批到组织架构的第 1 级。
6. **层级审批选"本级部门"要想到例外**：课件明确说这个选项适用于"不考虑部门负责人自己提交审批"的情形，负责人本人提交时要另行处理，别默认它能兜住所有情况。
7. **逐级审批的节点内不支持加签**：想在逐级审批里补人给意见，这条路径走不通，得换个节点类型。
8. **加签人只能提意见**：不能改变审批流程、也不能决定通过或驳回，别指望靠加签让某个人"放行"。
9. **阶段变更类审批流没有"审批通过后动作"**：只有节点完成后动作。想让阶段审批通过后锁单、发通知，必须配在节点后动作里。
10. **后动作配错位置就是配错时机**：节点上方是"后动作"（只管本节点），左下方"执行操作"是整条流程结束后才跑，两处不要混用。
11. **触发时机不止"新建时"**：作废、变更负责人、公海领取这类按钮点击都能触发审批，先想清楚业务上到底是哪个动作要卡审批。
12. **并行网关 ≠ 任务协作**：并行网关是所有分支全部完成后才往下走；只要其中一人处理完就够的，用任务协作节点。
13. **"更换负责人 + 数据锁定"是常用组合**：审批通过后锁定数据防改动，再把单子转给后续团队跟进，两个后动作一起配。
